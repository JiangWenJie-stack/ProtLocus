# miniprot 精度模式速度优化报告

日期：2026-09-10（2026-09-11 更新 extension DP 内核优化）
适用代码：`ProtLocus`（基于 miniprot 0.18-r281 的实验性分支）
测试数据：`Test_realdata/all_queries.fa`（1114 条蛋白）× 4 个真实基因组（小鼠 mouse、大鼠 rat、非洲爪蟾 frog、斑马鱼 zebrafish），`-t56 --accuracy --profile`

---

## 1. 原有算法：miniprot（miniprot_lh）

`miniprot_lh` 是官方 miniprot 0.18-r281 的原始实现，主流程为：

```
索引(4bit压缩基因组, 密码子翻译, 6-mer modimer采样)
  -> 粗略 anchor / 长程 chain
  -> 精确局部 5-mer 重链 (refine)
  -> 分段拼接 DP 比对 (mp_align)
  -> 过滤、排序、输出 PAF/GFF
```

其中与本次优化最相关的是 `mp_align` 的行为：

- 对每个候选比对区域，先用 `mp_filter_seed` 检查是否存在一段**可信 anchor**（tight run，anchor 数≥3、间距很小、阅读框一致）。
- **如果找不到可信 anchor，该候选区域直接被丢弃**（`r->cnt = 0; return;`），不会进行任何 DP 计算。
- 只有拥有可信 anchor 的候选，才会在 anchor 两端各做一次“端点延伸”DP（窗口大小由 `-e`/`max_ext`，以及与相邻候选区域的真实距离共同决定，见 `mp_cal_max_ext`），然后在可信 anchor 之间做窗口 DP 拼接。
- 候选保留策略也比较保守：`-N 30`（最多保留 30 个次优候选）、`-p 0.7`（次优候选打分需达到主候选的 70%）。

**结论：lh 版本天然速度快，因为它只对“已经比较确定是真比对”的候选做代价较高的 DP，对没有可信 anchor 的候选一律放弃。**

---

## 2. 我们为什么要做新算法（ProtLocus）

在实际比对中发现，lh 的“无可信 anchor 就丢弃”策略在**重复序列/旁系同源基因丰富的基因组**（如蛙、斑马鱼）上会造成明显的漏检：很多真实同源基因因为其比对区域内anchor 太稀疏、太分散或落在重复区域而拿不到一段可信 anchor，从而被直接丢弃，即使延伸/拼接 DP 本可以把它们正确地找回来。

为此在 lh 基础上开发了 `ProtLocus`（`--accuracy` 模式），新增了 6 项以召回率（recall）为目标的机制（详见 `ACCURACY.md`）：

1. **重复种子救援**：被 `-c` 阈值过滤掉的重复 posting list，按比例采样保留部分 anchor。
2. **按序列/链分组 chaining**：避免跨 contig/链错误合并候选链。
3. **放宽候选保留**：`acc_best_n=100`、`acc_pri_ratio=0.35`，比 lh 默认（30、0.7）保留更多、更远的候选，留给后续 DP 去伪存真。
4. **无可信 anchor 候选的“救援”DP（rescue）**：这是关键差异点——不再直接丢弃，而是对整个候选窗口做一次全窗口 DP（`full_dp=1, rescued=1`），只用 `acc_rescue_cells` 做一个总体 cell 数上限来防止极端窗口。
5. **可疑模型二次精修（junc-refine）**：对有非典型剪接位点/移码/终止子/短插入的候选做二次全窗口 DP 尝试替换。
6. **综合排序（rerank）**：结合覆盖度、剪接类型、移码、终止子等对候选重新打分排序。

这些机制共同作用，显著提高了在重复/旁系同源密集基因组上的查全率，但代价是**大量原本会被 lh 直接丢弃的候选现在都要跑一遍代价不小的 DP**——这正是速度问题的根源。

---

## 3. 速度问题定位（本次优化前的既有结论）

对 4 个真实基因组的 `--profile` 输出分析（细节见仓库记忆，非本报告重复展开）：

- **`align_s`（比对阶段）占总线程时间的 95%–98%**，是绝对的性能热点；`refine_s`、`chain_s`、`sketch_s` 等阶段合计不到 5%。
- `align_s` 内部，**`align_ext_s`（anchor 两端的“端点延伸”DP）占 95%–97%**，是热点中的热点；`align_gap_s`（anchor 间拼接 DP）和 `align_full_s`（整窗救援/强制全DP）各自只占 1%–2%。
- 在 `--accuracy` 模式下，**约 91%–98% 的 `dp_candidate`（视基因组而定）属于“无可信 anchor”的 `rescued` 候选**（例如蛙 91454/93542=97.8%，斑马鱼 80887/82375=98.2%），也就是第 2 节中第 4 项“救援”机制新增出来的工作量。

结论：**新增的 rescue 机制是速度回退的主要原因**，绝大多数比对时间花在了 lh 版本原本会直接跳过的候选身上。

### 3.1 本次会话之前已上线的优化（默认行为，非新增）

针对上面定位到的热点，之前已经验证并**默认上线**了一项零精度回退的优化：

- **rescued-only 跳过 io_end 二次重试**：`rescued` 候选的端点延伸 DP 原本在第一次窗口未能对齐到查询末端时，会用更宽松的罚分（`io_end`）再跑一次几乎同等代价的 DP；测得该二次重试对 92.9% 的延伸调用都会触发。经 A/B 验证，仅对 `rescued` 候选跳过这次重试，在 4 个基因组、1114 条 query 上**零召回率回退**（`oracle_only=0`，对照“无终端延伸上限”的严格 oracle），并带来 19%–36% 的 `align_ext_s` 降幅。
- 最终确认基准（3 次重复中位数 wall time）：小鼠 14.07s、大鼠 11.67s、蛙 20.69s、斑马鱼 18.79s，**合计 65.22s**；相比未加终端延伸上限的 `uncapped` 方案（合计 158.29s）提速 **2.43 倍**；相比本次会话之前的 `cap_r89` 基线（合计 81.49s）提速约 **19.9%**。

这是当前的默认基线，本报告后续的“新改进”均以此为对照基准（baseline）。

## 4. 本轮改进：允许损失少量精度换取更大速度提升

用户明确表示可以接受一定精度损失来换取更快的速度。基于此，做了以下工作：

### 4.1 新增 `--fast` 一键预设（已上线，默认关闭，需显式传参）

`--fast` 隐含开启 `--accuracy`，并设置：

```
--acc-end-ext=4500          # rescued 候选端点延伸的核酸(nt)侧窗口上限，默认 10000
--acc-end-aa-cap             # 开启 rescued 候选端点延伸的氨基酸(aa)侧窗口上限
--acc-end-aa-ext=800         # aa 侧窗口上限具体值，默认不生效(100000，相当于不限)
```

思路：既然大部分 DP 时间花在 rescued 候选的端点延伸窗口上，就把这个窗口从"最多探索 10000nt / 不限氨基酸长度"收紧到"最多 4500nt / 800aa"，减少每次 DP 的计算量。

**探索过程（选取该组参数前测试过的其他取值）：**

| 配置 | wall_s 变化（4基因组） | 精度代价 |
| --- | --- | --- |
| `--acc-end-ext=3000`（单独） | -23%~-27% | 过于激进：多个长蛋白（如 G6PI ~1900aa、NAMPT ~1980aa）比对分数明显下降，每基因组 30-40 条 query 分数变差、1-2 条彻底丢失 |
| `--acc-end-ext=6000`（单独） | -10%~-20% | 较温和，每基因组 0-1 条丢失、7-16 条分数下降 |
| **`--acc-end-ext=4500` + `--acc-end-aa-cap --acc-end-aa-ext=800`（采用）** | **-18%~-23%，四个基因组更一致** | 每基因组 0-2 条丢失、12-26 条分数下降 |

### 4.2 `--fast` 实测结果

| 基因组 | wall_s（默认基线） | wall_s（`--fast`） | 提速 | 丢失 query 数 | 分数下降 query 数 |
| --- | --- | --- | --- | --- | --- |
| 小鼠 mouse | 14.34s | 11.76s | -18% | 1 | 17 |
| 大鼠 rat | 13.36s | 10.90s | -18% | 0 | 12 |
| 蛙 frog | 24.37s | 20.10s | -18% | 2 | 26 |
| 斑马鱼 zebrafish | 23.68s | 18.14s | -23% | 0 | 20 |

（各基因组约 1000–1100 条 query 映射成功，“丢失”指原本能比对上、现在完全比对不上；“分数下降”指两边都能比对上，但打分变低）

已验证：`--fast` 与手动组合参数结果字节级一致；未加 `--fast` 时行为与之前完全一致（`make check` 全部通过，默认参数未改变）。

**结论：`--fast` 是本轮性价比最高的方案，已作为可选参数上线，默认不开启。**

## 5. 借鉴 `miniprot_lh` 思路的探索性实验（已测试，未采用为默认/新预设）

用户提出是否可以直接借鉴 lh 的做法。为此做了两组实验，直接复现 lh 的核心行为：

### 5.1 完全复现 lh：无可信 anchor 直接丢弃候选（`--acc-no-rescue`）

该参数已存在于代码中，效果等价于关闭第 2 节中第 4 项“救援”机制，行为与 lh 完全一致。

| 基因组 | wall_s（基线） | wall_s（`--acc-no-rescue`） | 提速倍数 | 完全丢失 query 比例 |
| --- | --- | --- | --- | --- |
| 小鼠 | 14.34s | 2.82s | 5.1x | 18.5% |
| 大鼠 | 13.36s | 2.97s | 4.5x | 10.1% |
| 蛙 | 24.37s | 4.86s | 5.0x | **61.9%** |
| 斑马鱼 | 23.68s | 3.24s | 7.3x | **67.0%** |

速度非常可观，但**精度损失是灾难性的**，尤其是重复序列丰富的蛙、斑马鱼——超过六成的 query 完全比对不上。这正好印证了第 2 节的结论：救援机制本来就是为了挽回 lh 会漏掉的这批候选，直接关闭等于放弃了 accuracy fork 存在的意义。**不采用。**

### 5.2 折中方案：候选保留范围收紧到 lh 默认值（`--acc-best-n=30 --acc-pri-ratio=0.7`，救援机制保持开启）

只把候选保留的宽松程度（`acc_best_n`/`acc_pri_ratio`）从 accuracy 模式默认的 100/0.35 收紧回 lh 默认的 30/0.7，救援机制本身不关闭。

| 基因组 | wall_s（基线） | wall_s（收紧候选保留） | 提速倍数 | 完全丢失 query 比例 | 分数下降 query 比例 |
| --- | --- | --- | --- | --- | --- |
| 小鼠 | 14.34s | 4.41s | 3.25x | 0.8% | 12.6% |
| 大鼠 | 13.36s | 4.27s | 3.1x | 1.3% | 5.6% |
| 蛙 | 24.37s | 10.93s | 2.2x | 9.0% | 35.5% |
| 斑马鱼 | 23.68s | 10.80s | 2.2x | 10.7% | 27.8% |

比完全关闭救援温和不少，速度也很可观，但精度代价仍然明显大于 `--fast`（尤其蛙、斑马鱼三分之一左右的 query 分数变差），风险高于本次会话确立的“可接受”标准。**未采用为默认或新预设，仅作为已有参数组合供用户按需自行选用。**

## 6. extension DP 内核等价优化（2026-09-11）

候选初筛无法安全区分弱同源与噪声后，优化目标转向已确定要执行的
`ns_global_gs16b()` 端点延伸 DP 本身。该方案不减少候选、不缩小搜索窗口，
也不改变打分、X-drop 或端点选择规则。

### 6.1 实现

- 在原 128-bit 热循环中复用 `H1[j]` 和 `H1[j-1]`，消除每个 SIMD 段的两次重复加载。
- 为 x86_64 增加 256-bit AVX2 extension 专用内核，每条向量同时计算 16 个
  16-bit DP lane；运行时通过 CPU capability 自动分派，无需新增命令行或构建参数。
- AVX2 仅用于不生成 traceback 的左右端点延伸；global/CIGAR 路径保持原实现。
- 不支持 AVX2 的 x86_64 继续使用 SSE2，ARM 继续使用 NEON，发布二进制的最低 CPU
  要求没有变化。

### 6.2 正确性验证

- 新增 7 aa 与 19 aa 的左右 extension 固定结果测试，分别覆盖 128-bit 回退、
  AVX2 跨 128-bit lane 移位和非整向量 padding。
- 2,000 组确定性随机左右 extension 输入逐项比较原 SSE2 与 AVX2 的
  `score`、`nt_len`、`aa_len`，结果完全一致。
- DPP3 集成输出 SHA-256 均为
  `d303e5f39bf5c0002421bbc7d8cc3adf7827ef2610e32619b226d556cf343d04`。
- mouse、rat、frog、zebrafish 的所有配对运行均通过完整 PAF `cmp`，不是只比较
  mapped query 数或最佳分数。
- `make check` 全部通过；OpenCL 后端未编译时 GPU 测试按设计跳过。
- 在 `ProtMine` 环境（GCC 15.3、`libasan.so.8.0.0`）中启用 AddressSanitizer
  和 LeakSanitizer 后，完整测试同样通过，未发现内存或对齐错误。

### 6.3 性能结果

环境：Intel Xeon Gold 6330，`-t56 -Iu --accuracy --profile`，1114 条蛋白，
原 SSE2 与新 AVX2 交替运行，每项取 3 次中位数。

| 基因组 | SSE2 `align_ext_s` | AVX2 `align_ext_s` | extension 耗时下降 | SSE2 real time | AVX2 real time | 端到端耗时下降 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| mouse | 600.20s | 514.65s | 14.3% | 18.34s | 15.82s | 13.7% |
| rat | 555.89s | 463.41s | 16.6% | 18.35s | 15.84s | 13.7% |
| frog | 1160.89s | 1016.63s | 12.4% | 31.08s | 26.10s | 16.0% |
| zebrafish | 1069.53s | 906.69s | 15.2% | 26.74s | 22.92s | 14.3% |
| **四者合计** | **3386.51s** | **2901.38s** | **14.3%** | **94.51s** | **80.68s** | **14.6%** |

AVX2 理论 lane 数是 SSE2 的两倍，但实际收益低于 2 倍，因为序列预处理、lazy-F、
端点归约和多线程内存带宽并未同比缩减。尽管如此，该优化不引入精度取舍，且直接作用于
占 alignment 时间绝大多数的热点，因此作为默认自动优化保留。

## 7. 总体结论

1. **lh 的速度优势来自于“做更少的工作”**：不救援无可信 anchor 的候选、候选保留范围更窈。这与 `ProtLocus` 存在的目的（找回 lh 会漏掉的重复/旁系同源基因）是根本性的取舍矛盾——**不可能既要 lh 的速度，又要 fork 现有的召回率**。
2. 单纯缩小 rescued 候选的 DP 搜索窗口（`--fast` 的思路）是本轮验证下来**性价比最高、代价最可控**的方案：约 18%–23% 的整体提速，每个基因组只有 0–2 条 query 完全丢失。
3. 直接照搬 lh 的"丢弃无锚点候选"或大幅收紧候选保留范围，虽然速度提升非常可观（2.2x–7.3x），但在重复序列丰富的基因组上会造成 10%–67% 的 query 完全丢失，风险远超本次会话确立的“可接受精度损失”尺度，**不建议默认启用**。
4. 对 extension DP 内核做等价的 AVX2 向量化，可在不改变任何 PAF 记录的前提下将
  extension 耗时降低 12.4%–16.6%，应优先于会牺牲召回率的候选裁剪策略。

### 建议

- 若可接受"少量、可控"的精度损失换取约 20% 的整体提速：直接使用 `--fast`。
- 在支持 AVX2 的 x86_64 CPU 上无需额外参数，extension DP 内核加速会自动启用。
- 若需要更极端的速度、且能接受成倍的精度损失（例如目标基因组重复序列很少、或后续会用其它方法补充比对结果）：可自行尝试 `--acc-no-rescue` 或 `--acc-best-n=30 --acc-pri-ratio=0.7`，但需要明确知晓并接受上表中的精度代价，不建议在没有真值数据验证的情况下用于正式生产环境。

## 8. 实验方法说明

- **数据集**：`Test_realdata/all_queries.fa`（1114 条蛋白）分别比对到 4 个真实基因组索引（小鼠、大鼠、蛙、斑马鱼）。
- **精度评价脚本**：`Test_realdata/compare_recall.py`，对 baseline 和候选方案的 PAF 输出按 query 取最高 `AS:i` 分数比较，统计：
  - `lost`：baseline 能比对上、候选方案完全比对不上
  - `gained`：baseline 比对不上、候选方案能比对上
  - `shared_worse` / `shared_better`：两边都能比对上，但分数变低/变高
- **运行参数**：`-t56 --accuracy --profile`，单次运行（此前已验证同配置在该数据集上运行结果稳定可重复）。
- **基线（baseline）**：当前代码默认参数（即已包含第 3.1 节的 rescued-only 重试跳过优化），对应 `--acc-end-ext=10000 --acc-end-retry=89`（均为默认值，无需显式指定）。
- **第 6 节内核基线**：由同一源码、同一编译器生成，仅将 `nasw-sse.c` 替换为
  AVX2 改动前保存的汇编对象；每组按相反顺序交替运行，以减小缓存和节点负载偏差。
